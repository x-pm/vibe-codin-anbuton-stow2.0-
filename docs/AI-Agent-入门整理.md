## 一、本章在讲什么

AI Agent 不再是「你问一句、它答一句」，而是能：

- **自主规划**执行步骤  
- **调用工具**完成任务  
- **根据结果**调整策略  

常见产品形态：Cursor（写代码）、Deep Research（调研）、Manus（浏览器任务）、豆包手机助手、Pine AI（打电话办事）等。

本章是全书的**概念地图**：公式、循环、Harness、编排与设计模式。先建立整体印象即可，细节在后续章节展开。

## 二、核心公式

### 2.1 最小工程公式

```text
Agent = LLM（大脑） + 上下文（眼睛） + 工具（手脚）
```

| 直觉 | 工程组件 | 含义 |
|------|----------|------|
| **大脑** | LLM | 理解意图、规划、决策（预训练知识 + 后训练策略） |
| **眼睛** | 上下文 | 每个决策点可见的信息：观察、记忆、知识、状态、进展 |
| **手脚** | 工具 | 感知/改变外部世界的接口：定义、协议、适配器 |

**边界：** 公式描述 Agent **内部**实现，**不包含** Environment（环境）。

### 2.2 Agent ↔ Environment 闭环

```text
环境 → 观察 → Agent 决策 → 行动 → 改变环境 → 新观察 → …
```

环境包括：文件、数据库、网页、用户、其他 Agent、物理/仿真世界。

### 2.3 Model–Harness 结构

| 层 | 职责 |
|----|------|
| **Model** | 策略决策（LLM） |
| **Harness** | 构造上下文、暴露工具、维护循环与状态、权限/验证/纠正 |

生产形态：

```text
Agent = Model + Harness
Harness = 上下文管理 + 工具接口 + 约束 + 验证 + 纠正
Agent ↔ Environment
```

Harness 是 **Agent 边界内、模型之外**的治理层；沙箱里的文件、外部库、网页本身属于 Environment。

## 三、观察空间与动作空间

**观察通道 + 动作接口 = Agent 与世界的边界。**

- 没进上下文的信息 → 模型「看不见」  
- 没开放的动作 → 模型只能给文字建议  

**模型固定时，提升表现最主要的工程手段，往往是扩展上下文与工具（观察/动作空间）。**

案例：

| 产品 | 突破点 |
|------|--------|
| **Manus** | 合并 Deep Research + Coding + Computer Use 的观察/动作空间 |
| **OpenClaw** | 接到消息渠道与本地/云文件，把接口延伸到用户数字生活 |

不同类型 Agent 对比（摘要）：

| 产品类型 | 感知 | 行动 | 策略特点 |
|----------|------|------|----------|
| Coding Agent | 代码、终端输出 | 搜索/读写/执行 | 增量开发 → 测试 → 修复 |
| Deep Research | 搜索结果、网页 | 搜索/阅读/写报告 | 迭代深化 |
| Computer / 手机助手 | 截图、UI 状态 | 点击/滑动/输入 | 感知 → 操作 → 验证 |
| 办事 Agent | 账单、账户信息 | 电话/邮件/填表 | 多步协商 |

共同特征：**开放式动作空间**、**内部思考**、**持续交互**。

## 四、工具（手脚）

### 4.1 五类工具

| 类型 | 作用 |
|------|------|
| **感知** | 搜索、读文件、API、数据库 |
| **执行** | 跑代码、改文件、系统命令、调 API |
| **协作** | 委托子 Agent、请求人类确认、多 Agent 协调 |
| **事件触发** | 邮件/定时/Webhook 驱动 Agent 启动（被动输入） |
| **用户沟通** | 消息、语音、邮件等主动通知用户 |

### 4.2 工具调用四步

1. 声明可用工具（名称、用途、参数）  
2. 模型决定是否调用、调哪个、传什么参  
3. 执行结果追加进上下文  
4. 模型据此继续行动或回答  

→ 这是 **ReAct** 的基础。

### 4.3 工具设计原则

- 从**最窄能力**起步，再按需扩展  
- **通用工具**（如受限 Python 沙盒）利于组合；**专用工具**约束高风险操作（支付、删除、发信、部署）  
- 沙盒：隔离、默认无网、路径限制、资源上限  
- 接口要清晰；错误处理与权限要到位（MCP 降低接入成本）

## 五、LLM（大脑）

- 解析真实意图 → 拆解步骤 → 持续判断「下一步 / 是否调工具」  
- **内部思考**：行动前推演，不改变环境，但提高行动质量  
- **模型即 Agent**：后训练把工具调用决策内化为原生能力；Harness 反而更重要（把强模型「套上缰绳」）  
- 立场：**方向上模型会逐步「吃掉」Harness；节奏上工程仍要补模型当下做不稳的部分**

### 能力更新三条路径

| 路径 | 何时 | 特点 |
|------|------|------|
| **上下文适应** | 当前任务内 | 快、便宜，不持久 |
| **外部产物** | 跨任务 | Prompt / Skill / 程序 / 知识文档，可审计 |
| **参数更新** | 训练周期 | 泛化强，成本高 |

## 六、上下文（眼睛）

每次调用 LLM 的上下文通常由五部分构成：

| 组件 | 说明 |
|------|------|
| **系统提示词** | 身份、权限、行为准则；可含用户记忆 |
| **工具定义** | 可用工具的 schema（常为静态前缀） |
| **用户消息** | 用户输入 + 可能的 RAG 知识 |
| **模型回复** | reasoning / content / tool_calls |
| **工具结果** | 执行回传，供下一步决策 |

```text
上下文 = 静态前缀（系统提示 + 工具定义） + 轨迹（动态消息历史）
```

**消融实验结论（实验 1-1）：**  
缺工具定义 → 不会用工具；缺工具结果 → 盲目循环；缺思考过程 → 决策不连贯；缺历史 → 重复犯错。  
**Agent 只能基于它看到的信息决策。**

## 七、ReAct 循环

```text
想 → 做 → 看 → 想 → 做 → 看 … 直到完成
```

最小骨架（伪代码）：

```python
trajectory = [user_request]
repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)
    if decision has no tool call:
        return decision.answer
    for call in decision.tool_calls:
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

要点：

- 轨迹便于解释、调试、沉淀知识、做强化学习  
- 「模型即 Agent」示例：Kimi K3（长链工具调用稳定）、GPT-5.6 + 内置搜索/代码解释器（Deep Research 风格）  
- RL 内化的是**调用决策策略**；工具执行仍在框架/服务端基础设施里

## 八、Harness 工程

### 8.1 为什么需要

Demo 能跑 ≠ 产品可靠。幻觉、选错工具、错误无法恢复，都靠 Harness。

### 8.2 五要素

| 要素 | 职责 | 例子 |
|------|------|------|
| **Context** | 信息充分 | 系统提示、知识库、状态栏 |
| **Tools** | 接口清晰 | MCP、搜索、代码解释器 |
| **Constrain** | 行为边界（默认关闭） | 工具需授权 |
| **Verify** | 校验结果（优先结构化数据） | Linter、返回校验 |
| **Correct** | 重试 / 回退 / 熔断 | 静默重试、交还人工 |

行业趋势：从「能做事」→「**可靠地做事**」。竞争力往往在模型之外的 Harness。

### 8.3 工程范式演进

```text
提示工程 → 上下文工程 → Harness 工程 → Loop 工程 → Graph 工程
```

层层包含，不是彼此替代。模型能力趋同后，差异更多在工程。

### 8.4 Anthropic 三原则

1. **保持简单** — 够用再加复杂度  
2. **保持透明** — 展示规划与轨迹，建立信任  
3. **设计好 ACI**（Agent-Computer Interface）— 从 Agent 视角设计接口，用设计防呆（Poka-yoke）

## 九、模型选型（思路）

- 闭源 / 开源：按任务实测，不要只看榜  
- 看策略边界：产品是否允许你调用某能力  
- Agent 多数需要 **Reasoning（思考）** 模型  
- 关注 **输出速度**（多轮延迟累积）与 **多模态** 需求

## 十、编排：工作流 vs 自主 Agent

### 选择顺序

```text
单次 LLM 调用 → 工作流（固定路径） → 自主 Agent（动态决策）
```

用延迟和成本换性能时，要算这笔账。

| | 工作流 | 自主 Agent |
|--|--------|------------|
| 路径 | 代码预先写死 | 按环境反馈实时决定 |
| 优点 | 流程可控、安全面小 | 灵活、适合开放问题 |
| 缺点 | 难覆盖例外 | 成本高、易复合错误 |
| 适合 | 订票：身份→搜航班→付款→确认 | Coding、Computer Use、深度调研 |

实践中常**混合**：合规关键步骤用工作流，灵活部分用自主；需设**停止条件**（完成 / 达最大轮数 / 不可恢复错误）。

框架选型不必死记（变化快），优先：**少抽象、能专注业务**（Agents SDK、LangGraph、n8n、Dify、CrewAI、OpenClaw 等）。

## 十一、护栏与安全

按**被绕过难度**分三层（越下层越不依赖模型判断）：

| 层 | 管什么 | 要点 |
|----|--------|------|
| **上下文层** | 模型能看到什么 | 相关性/安全分类、内容审核、规则过滤；越狱 vs 提示注入 |
| **执行层** | 模型能做什么 | 工具风险评级、沙盒、人在回路、输出/PII 检查 |
| **数据层** | 世界最终如何被改写 | DB 行级安全、约束、受控存储过程——即使注入成功也可拦截 |

**人工干预：** 超失败阈值、高风险不可逆操作时移交人类。  
注意护栏的**误拒绝**：评估时既测「该拦的拦了」，也测「该放的放了」。

## 十二、贯穿全书的五个设计模式

| 模式 | 一句话 |
|------|--------|
| **提议者—审核者** | 产出与评判分上下文；自审不可靠 |
| **渐进式披露** | 先给目录，再按需加载细节 |
| **只增不改** | 追加演进，利于缓存、重放、审计 |
| **边界集 + 保留集** | 改动要同时测「应变」与「不应变」样本 |
| **最小 diff + 可回滚** | 小改、可溯源、可单独回滚 |

## 十三、本章小结（速记）

1. **Agent = 大脑 + 眼睛 + 手脚**（LLM + 上下文 + 工具）  
2. **扩展眼睛/手脚** 往往比换模型更立竿见影  
3. **上下文决定决策上限**；ReAct = 追加轨迹推进任务  
4. **Harness** 是生产竞争力：约束、验证、纠正  
5. **先简单调用 → 工作流 → 自主 Agent**  
6. **安全是架构问题**：上下文层 / 执行层 / 数据层  
7. 五个设计模式贯穿后续章节

## 十四、思考题（原书，无标准答案）

1. 只能增强一项：更强模型 / 更丰富上下文 / 更多工具，选哪个？何时改主意？  
2. ReAct 中缓存读取近似二次增长，如何降低？  
3. 「模型即 Agent」与 Harness 重要性上升如何共存？  
4. 除工具结果缺失外，还有哪些无限循环场景？如何检测终止？  
5. 用感知/行动/策略分析一个你常用的 AI 产品。  
6. 航班订票系统：工作流还是自主？能否混合？  
7. 同一工具在不同参数下风险不同，如何做动态风险评估？  
8. 何时受限动作空间优于开放式？  
9. 人工不在线或回复模糊时，Agent 如何优雅移交？  
10. 举一个可能随模型变强而过时的工程手段。
